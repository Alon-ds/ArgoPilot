# מטלה P2 — מדריך להסבר והדגמה

המקורות הקובעים הם [P2](https://github.com/alonitac/OzVeruach26/blob/main/tasks/p2.md)
ו[מדריך Actions](https://github.com/alonitac/OzVeruach26/blob/main/tutorials/github_actions_intro.md).
חשוב להבחין: תרגיל Actions הוא חלק מתהליך העבודה; הוא אינו כל מטלת P2.

## 1. מה המערכת עושה

המטרה היא לענות למגדל האם להשקות היום ולכמה דקות. ה־registry מחזיק
עובדות על החלקה. שירות מזג האוויר מספק תחזית. המתכנן מחבר ביניהם באמצעות
נוסחאות קבועות. הממשק מציג למשתמש את התוצאה. השירותים מתקשרים ב־HTTP;
הם אינם מייבאים קוד אחד של השני.

## 2. Git ו־CI

עובדים ב־branch ומציעים שינוי דרך PR אל main. כל job ב־GitHub Actions
מקבל מכונה נקייה, מבצע checkout, מתקין תלויות מה־lockfile ומריץ בדיקות.
`uv sync --locked` נכשל אם הקובץ אינו מתאים להגדרת התלויות.
מטריצת Python בודקת את אותו שירות בשתי גרסאות, 3.12 ו־3.13.

בדיקת area מוסיפה נתון נגזר: `area_dunam = area_m2 / 1000`. לדוגמה,
חלקה בגודל 800 מ״ר היא 0.8 דונם. הבדיקה צריכה לאמת ערכים בפועל וגם 404.

Coverage בודק אילו שורות וענפי תנאי הורצו. `fail_under = 100` חייב להופיע
תחת `[tool.coverage.report]`; תחת `run` הוא נזנח. 100% אינו הוכחת נכונות,
ולכן הבדיקות כוללות גם השוואת תוצאות ולא רק קודי HTTP.
דוח HTML נשמר כ־artifact גם כשהבדיקה נכשלת.

`uv audit` בודק גרסאות תלויות מול מאגר בעיות ידועות. הוא אינו בודק את
נכונות התכנון ואינו מבטיח שאין חולשות לא ידועות. Required Checks מונעים
merge עם בדיקות אדומות רק אם תוכנית GitHub והרשאות הריפו אוכפות אותם.

## 3. מסד הנתונים

SQLAlchemy הוא שכבת הגישה המשותפת ל־SQLite ול־PostgreSQL. בוחרים מסד
באמצעות DATABASE_URL בלבד. ה־API ומזהי ה־seed נשארים עקביים בין המסדים.
הערכים בשאילתות נשלחים כפרמטרים, לא מחוברים לתוך SQL.
טרנזקציה שומרת שינוי שלם, או מבטלת אותו במקרה של חריגה.

`uv run python -m seed` יוצר טבלאות ו־15 רשומות במסד ריק. הוא מסרב לרוץ
על סכימה קיימת כדי לשמור נתוני משתמש. בדיקות PostgreSQL משתמשות במסד
זמני ומבצעות קריאה, יצירה, עדכון ומחיקה של רשומת הבדיקה שלהן בלבד.

## 4. מזג האוויר

הלקוח מבקש קואורדינטות ומספר ימים. המתאם מתרגם את שדות הספק למודל שלנו.
שתי נקודות באותו תא של 0.1 מעלות חולקות cache. כל עוד התחזית טרייה אין
פנייה נוספת לספק. אחרי כשל מנסים שוב; אפשר להחזיר תחזית קודמת רק עם
סימון stale ובתנאי שהיא מכסה את התאריכים הנדרשים. בלי נתונים תקינים מחזירים
503. אסור להמיר שדה חסר לאפס, כי אפס עלול להיראות כהמלצה לא להשקות.

## 5. מתכנן ההשקיה

מחקר FAO-56 נמצא ב־`services/planner-service/docs/research/fao56.md`.
ה־skill `irrigation-calc-reference` מתעד את ההנחות והנוסחאות המחייבות.
מקדם Kc משתנה לפי הגידול וגילו; `ETc = ET0 × Kc`. עומק מים של מילימטר
על מטר רבוע הוא ליטר, לכן `litres = depth_mm × area_m2`.

מספר הטפטפות מחושב מהשטח וממרווחי השורות והטפטפות; הספיקה הכוללת היא
מספר הטפטפות כפול ספיקה לטפטפת. דקות הפעלה הן נפח חלקי ספיקה לשעה כפול 60.
מעגלים דקות כלפי מעלה. דלי הקרקע עובר מיום ליום: גשם ממלא, צריכת הגידול
מרוקנת. במודל התרגיל משקים כשצפוי לרדת מתחת לחצי הקיבולת.

אין כאן מד לחות או היסטוריית השקיה: התחלת הדלי המלא היא הנחת מודל מפורשת,
לא מדידה. אין לתת לתוכנת AI להמציא או לשנות את מספרי ההשקיה בזמן ריצה.
פרטי ההבדל בין סף התרגיל לבין FAO מתועדים במסמך התחום.

## 6. הממשק

העמוד הראשי מציג חוות וחלקות. עמוד החלקה מדגיש את המלצת היום, ואז את
התוכנית לשבעה ימים. תחזית ישנה ושירות לא זמין מקבלים הסבר גלוי.
בקשות השירותים רצות בשרת Next.js דרך src/lib; הדפדפן אינו פונה ישירות
לשירותי Python. במובייל צריך לבדוק רוחב 375 פיקסלים ללא גלילה אופקית.

## 7. מה להציג בהדגמה

1. PR והבדיקות שלו, כולל artifact, בנפרד מבדיקות מקומיות.
2. pyproject.toml: סף coverage, branch coverage וה־lockfile.
3. שינוי DATABASE_URL והרצת seed במסד ריק.
4. GET תחזית פעמיים, כדי להדגים שימוש ב־cache.
5. שלושה מקרי חישוב ידניים מול פלט המתכנן.
6. הממשק ברוחב טלפון ותצוגה במקרה של שירות חסר.
7. תוצאות benchmark: קצב, משך, p95, מספר שגיאות ותנאי המדידה.

אין להציג דרישה כ״בוצעה״ רק מפני שיש עבורה קוד. ההוכחות והחסימות בפועל
נרשמות ב־`docs/p2-verification.md`.
